# 개발 기록 기준

이 문서는 완료한 개발을 다음 사람이나 AI agent가 대화 이력을 읽지 않고 이어받을 수 있게 남기는 기준입니다. 연구 보고서, 작업 등록부, session handoff의 목적을 섞지 않습니다.

## 문서 역할

- `docs/architecture.md`: 현재 시스템의 경계와 문서 탐색 시작점입니다. 구조나 경계가 바뀔 때만 갱신합니다.
- `docs/worktree-tasks.md`: 활성·차단·완료 작업의 짧은 등록부입니다. 실제 Git 상태와 항상 일치해야 합니다.
- `docs/development-records/<YYYY-MM-DD>-<slug>.md`: 작업별 영구 기술 기록입니다. 완료·차단·중단 작업마다 하나를 저장소에 커밋합니다.
- `HANDOFF.md`: 현재 세션 또는 현재 재개 작업의 짧은 상태입니다. 완료 작업 전문을 계속 누적하지 않습니다.
- 저장소 밖 audit 디렉터리: 큰 로그, 원시 데이터, 화면 캡처, 재현 산출물입니다. 개발 기록에는 절대 경로, manifest와 필요한 해시만 적습니다.

## 완료 절차

1. 변경 영향에 맞는 문서를 갱신합니다. 화면·사용 흐름은 README 또는 기능 문서, 운영·배포는 runbook, API·설정·데이터 계약은 해당 계약 문서입니다. 문서 변경이 필요 없으면 이유를 개발 기록에 적습니다.
2. `docs/development-records/`에 날짜와 작업 slug로 Markdown 기록을 만듭니다. slug는 작업 등록부의 slug와 같습니다. 같은 작업을 재개하면 같은 기록을 갱신합니다.
3. 작업 등록부에 개발 기록 경로, handoff 경로, 통합 SHA와 검증 상태를 적습니다.
4. handoff 스킬을 실행해 현재 재개 정보만 남깁니다. 기록과 handoff에는 비밀값, 계좌 식별자, 원시 인증 응답을 넣지 않습니다.

코드가 없는 조사·문서 작업도 결정이나 다음 행동이 남으면 같은 기록을 만듭니다. 아주 작은 오탈자 수정은 변경된 사용자 문서와 검증 결과만 남기면 됩니다.

## 작업별 기록 양식

```markdown
# <작업 제목>

- 상태: 완료 | 차단 | 중단
- 기록 시각: <UTC ISO-8601>
- 작업 slug: `<slug>`
- 기준/통합: `<base SHA>` / `<main SHA 또는 없음>`
- 범위: <무엇을 바꾸고 무엇을 의도적으로 보존했는지>

## 변경과 결정

- <중요 변경, 파일 또는 계약 경로, 결정 이유>

## 문서·계약 영향

- 사용자 문서: <갱신 경로 또는 해당 없음과 이유>
- 운영 문서: <갱신 경로 또는 해당 없음과 이유>
- API·설정·데이터 계약: <갱신 경로 또는 해당 없음과 이유>

## 검증

- `<실행 명령>` — <통과/실패와 핵심 결과>
- 실행하지 않은 검사: <이유>

## 안전·운영 상태

- <PAPER/실주문, 서비스, 데이터, 배포, 원격 push의 실제 변경 여부>

## 증거와 재개

- audit: `<안전한 경로>`; manifest: `<경로 또는 없음>`; hash: `<필요할 때만>`
- 남은 작업·차단 조건: <없음 또는 구체적 조건>
- 다음 시작: <첫 번째 읽기/검증/행동을 한 문장으로>
```

검증하지 않은 결과를 통과로 쓰지 않습니다. 파일 경로는 파일명만 나열하지 말고 왜 다음 작업자가 읽어야 하는지 함께 설명합니다. 실제 주문, 외부 배포, 데이터 변경, 서비스 상태, 원격 push는 수행 여부를 명시합니다.

# 프로젝트 workflow

작업 시작부터 완료까지 필요한 판단과 원본 문서의 안내입니다. 매 작업은 [공통 메모리](../MEMORY.md)를 먼저 읽고 이 문서에서 해당 경로를 선택합니다. 이미 읽었고 바뀌지 않은 지침은 다시 읽지 않습니다. 세부 운영 명령·모델·연구 조건은 연결된 정본에서 확인합니다.

## 작업 흐름

| 단계 | 판단과 행동 | 다음 단계로 넘길 결과·원본 |
| --- | --- | --- |
| 1. 현재 상태 확인 | Git 변경·worktree·runner와 관련 작업의 소유 범위를 확인하고 기존 근거를 재사용합니다. 수동 변경 전 pause·service 중지·inactive 확인을 수행합니다. | [메모리의 탐색 순서](../MEMORY.md#필요한-맥락만-읽는-순서), [구조 안내](architecture.md), [실행기 제어](development-runner.md#상태와-수동-제어) |
| 2. 다음 결과 선택 | 요청이 어떤 비교·기각·차단 해소 또는 필요한 정확성·복구에 기여하는지 정합니다. 현재 자료로 검증할 수 없는 성과를 완료 조건으로 약속하지 않습니다. | [목표와 우선순위](autonomous-trading-lab.md#17-목표-기반-지속-운영) |
| 3. 범위 고정 | 목표, 입력, 소유 범위, 산출물, 검증 방법, 종료 조건을 짧게 정합니다. 관련 등록부 항목을 만들거나 갱신합니다. | [작업 등록부](worktree-tasks.md), [작업 배정 양식](worktree-workflow.md#작업-지시와-기록) |
| 4. 조사·계획·수행 | 아래 작업 경로와 agent 규칙을 적용합니다. 구현 소유자는 한 명으로 두고, 작업별 환경·출력 경로를 분리합니다. | 제한된 계획과 산출물, [격리 기준](worktree-workflow.md#실행-환경-격리) |
| 5. 검증·통합 | 영향 범위 검사와 필요한 독립 검토를 거쳐 로컬 main에 순차 통합하고 통합 검증을 수행합니다. 실패하면 완료로 표시하지 않습니다. | [검증·통합 및 실패 대응](worktree-workflow.md#검증과-통합) |
| 6. 기록·다음 행동 | 바뀐 사용자·운영 문서, 개발 기록, 등록부와 필요한 handoff를 갱신합니다. 산출물 보존 후 정리하고 재개 조건 또는 다음 행동을 남깁니다. | [완료 절차](worktree-workflow.md#완료와-handoff), [개발 기록 기준](development-records.md), 아래 유용성 평가 |

## 작업 경로 선택

- **작고 범위가 확정된 수정·문서 정리:** 짧은 계획과 필요한 최소 위임으로 처리합니다. 중간 이상 코드 작업의 전체 역할 체인을 기계적으로 적용하지 않습니다. 해당 작업의 필수 검사·검토·완료 기준은 유지합니다.
- **중간 이상 기능·버그 작업:** 아래 `explore → plan → code/code_small → review` 순서를 적용합니다. 원인 미확인 장애는 재현·근거를 확보한 뒤 수정합니다.
- **연구·자료 준비:** [현재 연구 조건](research-mandate.md)과 [조건 JSON](research-mandate.json), [투자 로드맵](investment-development-roadmap.md)의 해당 단계를 먼저 확인합니다. 새 연구와 과거 동결 실험을 구분하고 기술 완료·자료 인수·투자 검증을 각각 판단합니다. 공개할 비교 결과가 있으면 [성과 공개 절차](research-progress-publication.md)를 적용합니다.
- **대기·차단·재개:** [연속 실행 원칙](continuous-development-session.md#continuous-execution-rule)에 따라 실제 시도와 재개 사건을 확인합니다. 같은 입력으로 실패한 조사를 반복하지 않고 독립 READY 작업을 검토합니다. 전역 pause·lock·권한 경계는 유지합니다.

## 도움이 되는지 판단하는 방법

이 workflow의 목적은 다음 검증 가능한 결과까지 드는 시간과 재작업을 줄이는 것입니다. 문서 작성량이나 agent 호출 수가 많다는 이유로 유용하다고 판단하지 않습니다.

1. 시작할 때 선택한 절차가 이번 작업의 어떤 불확실성이나 오류를 줄일지 한 문장으로 정합니다. 기존 계획·등록부에 적을 수 있으며 별도 보고서는 만들지 않습니다.
2. 완료 또는 차단 시 기존 개발 기록에 아래 세 줄을 남깁니다. 확인 가능한 시간·호출·토큰·재작업·검사 결과만 근거로 쓰며, 비교 자료가 없으면 절감 효과는 미측정으로 씁니다.
3. 중복 읽기·불필요한 위임·같은 검사 반복이 관찰되면 원본 재사용, 범위 축소, 안내 통합을 적용합니다. 필요한 정확성 검사·독립 검토·투자 안전 기준을 비용 절감 명목으로 생략하지 않습니다.
4. 개선할 근거가 생긴 때 이 문서 또는 해당 정본 한 곳을 수정하고 이유를 개발 기록에 남깁니다. 효과를 확인하지 못한 절차는 미확인으로 유지하고 반복되는 부담만 추가하지 않습니다.

```text
- workflow 판단: 도움 됨 | 부담 큼 | 아직 미확인 — 적용한 절차와 이유
- 근거: 재사용한 자료, 발견한 결함, 재작업·검사 결과; 시간·호출 절감은 측정 시에만 기록
- 다음 조정: 유지 | 축소 | 수정 — 대상과 이유, 또는 추가 변경 없음
```

## Agent 실행 규칙

실제 spawn CLI가 role 필드를 제공하지 않는 경우에는 [agent routing compatibility procedure](agent-tooling.md#roleless-cli-routing)를 따르고 `backend/jusik/agent_routing.py`의 model-only adapter를 사용합니다. 이 예외는 roleless CLI에만 적용하며 native interactive helper의 검사는 바꾸지 않습니다.

### 감독과 작업자 구성

- 중앙 정책의 supervisor가 감독을 맡습니다. 연구 가설, 우선순위, 작업 범위, 완료 기준을 정하고 결과 통합과 최종 판단을 담당합니다.
- 동시 active agent는 planner를 포함해 최대 4개입니다. 하위 agent는 총 3개 이하이며 중첩 위임도 이 한도에 포함합니다. 기본적으로 planner만 위임합니다.
- 각 워크트리의 개발은 중앙 정책에서 선택한 구현자 한 명이 담당합니다. 조사·계획·검증은 작업 난도와 역할별 모델 설정에 맞춰 배정합니다.
- 4개는 전체 상한이며 항상 모두 실행할 필요는 없습니다. 독립적으로 수행할 구체적인 작업이 있을 때만 투입합니다.
- 각 작업에는 목표, 입력, 담당 범위, 산출물, 검증 방법, 종료 조건을 명시합니다. 결과는 근거와 함께 요약하여 감독에게 전달합니다.

작업자의 책임은 다음과 같이 나눕니다. 아래 역할은 작업 분담 기준이며, 별도의 agent를 모두 동시에 생성하라는 의미는 아닙니다.

1. **조사:** 관련 코드, 데이터 출처, 데이터 흐름, 기존 구현과 관례를 확인합니다.
2. **실험:** 사전에 정한 조건으로 연구를 실행하고 결과와 실패 원인을 정리합니다.
3. **구현:** 확정된 계획에 따라 코드를 수정합니다. 작업별 구현 소유자는 한 명만 둡니다.
4. **검증:** 계산 오류, 미래 데이터 누출, 회귀와 검증 누락을 독립적으로 확인합니다.

### 실행 순서와 병렬화

중간 이상 규모의 기능 작업과 버그 수정에는 프로젝트 전용 custom agent를 사용합니다.

1. `explore`로 관련 코드, 데이터 흐름, 관례, 테스트를 조사합니다.
2. 조사 결과를 `plan`에 전달합니다. 범위가 제한된 계획과 완료 기준을 받습니다.
3. 확정한 계획을 작업별 워크트리의 구현 담당자에게 전달합니다. 복잡한 변경은 `code`, 제한된 반복 작업은 `code_small`을 사용하고 모델·effort는 중앙 profile에서 읽습니다. 로드된 역할이 현재 설정과 다르면 기대 모델·추론 수준과 `fork_turns=none`을 명시한 `agent_type=default` worker를 사용합니다. 작업별 구현 소유자는 한 명만 둡니다.
4. 구현과 검증 후 중앙 정책의 별도 `review`를 실행합니다. 중요한 지적은 원래 구현 담당자가 수정합니다. Astra는 서로 다른 Sol 가설의 반복 실패, 중대한 구조 변경·의견 충돌·원인 불명 장애, 실투자 후보 직전 독립 검토에서 근거를 남기고 최대 한 번 선택합니다. Astra가 없으면 Sol 독립 검토 또는 다른 READY 작업으로 진행하며 검증 기준은 유지합니다.

의존하는 단계를 병렬로 실행하지 않습니다. 독립적인 읽기 전용 조사와 검토는 병렬화할 수 있습니다. 실험과 검증 실행은 입력과 조건이 확정되고, 다른 작업과 출력 경로 및 변경 가능한 상태가 겹치지 않을 때만 병렬화합니다. 같은 코드나 공유 운영 데이터를 여러 작업자가 동시에 수정하지 않습니다.

주 supervisor가 사용자와 소통하고, 의견 차이를 정리하며, 최종 결과를 반환합니다. 거래 연구 결과는 agent 간 동의가 아니라 독립된 데이터와 테스트를 통한 재현성으로 판단합니다. 작업 분담의 효율은 총 소요 시간, 확인 가능한 토큰 사용량, 재작업 횟수, 검증 통과 여부로 평가합니다.

# 워크트리 운영 절차

## 목적과 구조

독립적인 개발 작업은 Git worktree로 분리합니다. Astra는 작업 분배와 통합을 담당하고, 각 Luna는 지정된 워크트리에서 개발합니다. 작업자 수와 조사·계획·구현·검증 순서는 루트 `AGENTS.md`를 따릅니다.

```text
/home/kwl/projects/
├── jusik/                   # Astra: 기준 저장소와 통합
├── jusik-market-data/       # Luna: 시세 수집 작업
└── jusik-backtest-metrics/  # Luna: 백테스트 지표 작업
```

작업 하나에 브랜치 하나, 워크트리 하나, 구현 담당자 하나를 배정합니다. 폴더를 복사하지 않고 `git worktree add`로 생성합니다. 슬러그는 `market-data`처럼 작업을 설명하는 소문자 영문·숫자·하이픈으로 작성합니다. 브랜치는 작업에 맞게 `feat/<slug>`, `fix/<slug>`, `docs/<slug>` 등을 사용합니다.

워크트리는 파일과 인덱스를 분리하지만 Git 객체·브랜치 정보·일부 설정은 공유합니다. 다른 폴더 접근을 차단하는 보안 경계는 아닙니다. 강제 격리가 필요하면 별도 컨테이너 또는 샌드박스를 사용합니다.

## 작업 준비와 생성

첫 개발 워크트리를 만들기 전에 `AGENTS.md`, 이 운영 문서와 작업 등록부의 확정된 변경을 검토하고 커밋하여 기준 커밋에 포함합니다. 해당 문서만 명시적으로 스테이징하고 관련 없는 사용자 변경이나 기존 handoff를 함께 커밋하지 않습니다. 이후 운영 규칙 변경도 새 작업의 기준 커밋에 포함되었는지 확인합니다.

1. Astra가 현재 변경 사항, 기존 워크트리와 브랜치를 확인합니다. 관련 프로젝트 지침과 기존 구현을 읽고 작업 범위를 정합니다.
2. 독립적으로 진행할 수 있는 작업만 병렬로 분배합니다. 공통 API나 스키마에 의존하면 계약을 먼저 확정하거나 선행 작업 통합 후 시작합니다.
3. 기본 통합 대상은 로컬 `main`입니다. 통합 대상 브랜치와 기준 커밋 SHA를 기록합니다. 같은 작업 묶음은 가능하면 같은 기준 커밋에서 시작합니다. 미커밋 변경은 새 워크트리에 자동 포함되지 않으므로 필요한 변경이 있다면 먼저 처리합니다. 사용자 변경을 임의로 옮기거나 커밋하지 않습니다.
4. 대상 폴더와 브랜치가 사용 중이면 덮어쓰지 않습니다. 기존 작업인지 확인하고 별도 슬러그를 지정합니다.

다음은 생성 예시입니다. `<base-sha>`는 확인한 실제 커밋 SHA로 바꿉니다.

```bash
git -C /home/kwl/projects/jusik status --short
git -C /home/kwl/projects/jusik worktree list
git -C /home/kwl/projects/jusik branch --list
git -C /home/kwl/projects/jusik rev-parse HEAD
git -C /home/kwl/projects/jusik worktree add \
  -b feat/market-data \
  /home/kwl/projects/jusik-market-data \
  <base-sha>
```

워크트리 생성 후 해당 경로의 `AGENTS.md`와 관련 하위 지침을 적용합니다. 운영 지침이 아직 커밋되지 않아 새 워크트리에 없다면 Astra가 현재 지침을 작업 지시에 명시적으로 전달합니다.

## 작업 지시와 기록

Astra는 아래 양식으로 작업을 기록하고 Luna에 전달합니다. 활성 작업 기록은 기준 저장소의 [작업 등록부](worktree-tasks.md)에서 Astra만 관리합니다. 작업 배정 전에 항목을 추가하고 상태 변경 시 갱신합니다. 작업자가 가진 등록부 사본은 수정하지 않습니다. 비밀값과 계정 식별자는 기록하지 않습니다.

```markdown
## <slug>

- 상태: 준비 | 진행 | 검증 | 통합 대기 | 완료 | 차단
- 목표와 완료 조건:
- 담당 Luna:
- 워크트리 절대 경로:
- 작업 브랜치:
- 기준 커밋 SHA:
- 통합 대상 브랜치:
- 입력과 선행 작업:
- 수정 허용 범위:
- 포트·테스트 DB·출력 경로:
- 검증 명령과 결과:
- 결과 커밋 SHA:
- 검토 결과와 남은 문제:
- 병합 직전 main SHA:
- 통합 커밋 SHA와 정리 여부:
- 통합 검증 실패 원인과 복구 결과:
- handoff 저장 경로와 갱신 여부:
```

Luna는 다른 작업자도 존재함을 전제로 지정 경로에서만 수정합니다. 다른 워크트리의 변경을 되돌리거나 공용 설정을 수정하지 않습니다. 모든 실행 명령에 작업 디렉터리를 명시하고, 편집 전 현재 경로와 브랜치를 확인합니다. 범위 밖 변경이 필요하면 Astra에 근거를 전달하고 작업 경계를 조정한 뒤 진행합니다.

워커 도구가 자동으로 작업 디렉터리를 바꾼다고 가정하지 않습니다. Luna 모델을 지정해 실행할 수 없다면 다른 모델을 Luna라고 부르지 않고 제한을 알립니다.

## 실행 환경 격리

- Python 가상환경, 프런트엔드 의존성 설치와 빌드 출력은 워크트리 내부에 둡니다. `.venv`, `node_modules`, `.next`를 다른 워크트리와 심볼릭 링크로 공유하지 않습니다.
- 서버 포트, 테스트 DB 또는 스키마, 컨테이너 프로젝트 이름, 로그·캐시·임시 파일·실험 결과 경로를 작업별로 지정합니다. 도구의 기본 경로가 공용인지 실행 전에 확인합니다.
- 환경 설정은 각 워크트리에서 별도로 준비합니다. `.env`와 인증 정보를 자동 복사하거나 커밋하지 않습니다. 문서에는 변수 이름과 자리표시자만 남깁니다.
- 공유 원천 데이터는 읽기 전용으로 사용합니다. 데이터 변경과 마이그레이션은 전용 테스트 DB나 복사본에서 검증합니다. 운영 데이터와 공용 서비스를 테스트 대상으로 사용하지 않습니다.
- 거래 검증은 모의 거래나 시뮬레이션으로 수행합니다. 실제 주문을 테스트에 사용하지 않습니다.
- CPU·메모리·외부 API 호출 한도는 폴더를 나눠도 공유됩니다. 충돌 가능성이 있으면 동시 실행 수를 줄이거나 순차 실행합니다.

## 검증과 통합

1. Luna는 작업 범위의 테스트·린트·설정된 타입 검사를 실행합니다. 프런트엔드 변경에는 빌드도 확인합니다. 실행하지 못한 검사는 이유를 기록합니다.
2. Luna는 변경 요약, 검증 결과, 남은 문제와 결과 커밋 SHA를 Astra에 전달합니다. 커밋에는 해당 작업 파일만 포함하며 비밀값과 생성물을 확인합니다.
3. Astra는 별도 검토 결과를 확인하고 중요한 지적을 해당 Luna가 수정하도록 합니다. 같은 작업에 구현 담당자를 추가하지 않습니다.
4. Astra만 기준 저장소의 로컬 `main`에 작업 브랜치를 순차 병합합니다. 사용자가 다른 통합 대상을 지정했다면 그 지시를 따릅니다. 실제 체크아웃된 브랜치와 작업 트리 상태를 확인하고 병합 직전 SHA를 기록합니다. 사용자 변경과 겹치면 통합을 보류합니다. 충돌 해결은 Astra가 조율하며 합의된 동작을 보존합니다.
5. 통합 후 영향 범위의 검사를 다시 실행합니다. 개별 브랜치 통과만으로 전체 완료를 선언하지 않습니다. 결과와 통합 커밋을 작업 기록에 남깁니다.

로컬 작업 브랜치 커밋과 통합은 배정된 개발 범위에서 수행합니다. 원격 push·PR·merge는 사용자가 요청한 범위와 권한을 따릅니다. 강제 push와 이력 재작성은 명시적 요청 없이는 수행하지 않습니다.

## 통합 검증 실패 대응

1. 검증이 실패하면 추가 병합과 해당 워크트리·브랜치 삭제를 중단합니다. 작업 상태를 차단으로 바꾸고 실패 명령, 원인 또는 미확인 사항, 통합 커밋 SHA를 기록합니다.
2. Astra는 실패가 작업 변경, 다른 작업과의 상호작용, 실행 환경 중 어디에서 발생했는지 확인합니다. 해당 Luna가 지정 워크트리에서 수정하도록 하고, 필요한 통합 상태를 반영하되 기존 커밋 이력과 작업자 변경을 보존합니다.
3. 수정 커밋을 검토·병합한 뒤 실패 검사와 관련 통합 검사를 다시 실행합니다. 통과하기 전에는 다음 병합과 완료 처리를 진행하지 않습니다.
4. 변경을 되돌려야 하면 Astra가 대상 커밋과 영향을 확인하고 설명한 뒤 `git revert`로 복구 커밋을 만듭니다. 병합 커밋은 부모 관계를 확인하여 mainline을 선택하고, fast-forward 병합은 이번 작업의 커밋 범위를 확인합니다. `reset --hard`나 강제 push로 이력을 지우지 않습니다.
5. 복구 후에도 검증합니다. 되돌린 작업은 완료로 표시하지 않고 재개 조건을 기록합니다. 이후 재병합은 revert 이력을 고려하여 수정 커밋이나 revert 복원 방식부터 확인합니다. 해결하지 못한 문제는 handoff에 남깁니다.

## 첫 운영 검증

첫 실제 개발 작업은 범위가 작은 작업 하나와 Luna 한 명으로 시작합니다. 아래 항목을 작업 등록부에 실제 결과로 기록한 뒤 병렬 작업 수를 늘립니다.

- 운영 문서가 기준 커밋과 새 워크트리에 포함되어 있습니다.
- 지정한 폴더·브랜치에서만 개발하고, 포트·테스트 DB·출력 경로가 다른 작업과 겹치지 않습니다. 사용하지 않는 자원은 해당 없음으로 기록합니다.
- Luna의 개발·검증·커밋과 Astra의 검토가 완료되었습니다.
- 로컬 `main` 병합과 통합 검증이 통과했습니다.
- 필요한 결과물을 보존한 뒤 워크트리를 정리하거나 보존 이유를 기록했습니다.
- handoff와 작업 등록부가 실제 Git 상태와 일치합니다.

운영 절차 확인을 위해 실제 주문이나 운영 데이터 변경을 수행하지 않습니다. 자동 생성·정리 스크립트는 첫 운영 결과에서 반복 작업과 실패 지점을 확인한 뒤 별도 작업으로 도입합니다.

## 완료와 handoff

사용자가 검증까지만 요청하는 등 종료 범위를 제한하지 않았다면, 개발 작업은 로컬 `main` 병합과 통합 검증 및 handoff 저장까지 수행해야 완료입니다. 이미 승인된 이 완료 절차를 수행하기 위해 매번 재확인하지 않습니다.

1. 통합 검증을 통과하면 아래 정리 기준에 따라 워크트리를 정리하거나 보존 이유를 기록합니다.
2. Astra는 `/home/kwl/.agents/skills/handoff/SKILL.md`를 읽고 해당 스킬의 저장 위치와 기록 절차에 따라 handoff를 저장합니다. 이는 세션 종료 여부와 별개로 개발 작업 완료 시 수행합니다.
3. handoff에는 목표, 검증된 변경, 결정, 검사 결과, `main`의 통합 커밋 SHA, 남은 작업, 워크트리 보존·정리 상태와 다음 시작점을 기록합니다. 활성 작업 기록과 실제 Git 상태가 일치하는지 확인합니다.
4. 최종 보고에 병합 결과, 검증 결과와 handoff 경로를 포함합니다. 병합이나 검증이 차단되면 완료로 표시하지 않고, 차단 원인과 재개 지점을 handoff에 남깁니다.

운영 규칙 자체를 논의하거나 편집하는 요청은 개발 작업 종료 또는 즉시 handoff 실행 요청으로 간주하지 않습니다.

## 정리

Astra는 통합과 검증이 끝난 작업만 정리합니다. 먼저 미커밋·미추적·무시된 파일과 미병합 커밋을 확인하고, 필요한 로그나 결과물을 보존합니다. 실행 중인 해당 작업의 서버와 프로세스도 종료합니다.

제거 대상과 보존 여부를 알린 뒤 정확한 경로로 `git worktree remove`를 사용합니다. `--force`나 폴더 전체 강제 삭제로 검사를 우회하지 않습니다. 브랜치 삭제는 통합 확인 후 별도로 처리합니다. 워크트리 삭제 시 미커밋 파일은 Git으로 복구할 수 없으므로 보존 확인 없이 진행하지 않습니다.

중단되거나 차단된 작업은 경로·브랜치·현재 상태·재개 지점을 기록하고 유지합니다. 새 세션에서는 작업 기록과 `git worktree list`, 각 작업의 실제 Git 상태를 대조한 뒤 재개합니다.
